# 架构

[English](../architecture.md) | **简体中文**

一次构建就是一个函数 —— `build(root)` → `SiteData` —— 后面跟着每种语言一次的
渲染。本文讲它的执行顺序,以及那些不那么显然的部分背后的理由。

```
描述符 ─▶ 标识 ─▶ 插件 ─▶ 远端补充 ─▶ 分面 / 区块 / 行
                                            │
git 历史 ──▶ 增长 · 历史 · 贡献者 ──────────┤
GitHub 缓存 ▶ 上游项目 · 登录名 · 生态 ─────┤
你的 markdown ▶ 文档 ───────────────────────┤
                                            ▼
                          SiteData ─▶ 每种语言一份站点
```

## 读描述符

`readers/xpkg_lua.py` 在 Lua 沙箱里执行每个 `pkgs/**/*.lua`,取出其中的 `package`
表。

这个沙箱与 **`libxpkg` 的 `register_loader_sandbox` 保持严格一致** —— 后者是包
管理器真正在用的参考实现。同样的全局量、同样的桩、同样的 `import()` 行为。这是一条
设计规则,不是巧合:一个描述符在这边能加载而在那边不能,就意味着网站和客户端对
「索引里有什么」产生了分歧;而一个比客户端解析得更多的网站,比解析得更少的更糟。

解析失败的描述符是警告,构建继续。一个描述符都没有才是错误。

## 标识与 slug

三个字段,绝不互相推导:

| 字段 | 是什么 | 取错了会怎样 |
|---|---|---|
| `display` | 人读的 | 只是不好看 |
| `slug` | URL 片段 | 一个包的页面覆盖掉另一个 |
| `install_ref` | 客户端 CLI 接受的 | 复制粘贴的命令跑不通 |

内核默认 `Identity.plain`:命名空间只是元数据,三个字段都是裸名字。插件显式选择
`Identity.joined`。

这个拆分之所以存在,是因为两个真实索引确实不一致。mcpp 把命名空间当作标识的一
部分 —— 你敲的是 `mcpp add nlohmann.json`。xlings 把它当作分类标签,名字是对着
*索引仓库*解析的,`xlings install xim.gcc` 根本不成立。一个「贴心地」帮你拼命名
空间的内核会毁掉后者;一个永不拼接的内核会毁掉前者的 URL。

标识分配完之后跑 `_check_slugs`。重复会中止构建,并指出冲突的描述符。这是插件链路
上唯一的硬失败,之所以硬,是因为它拦住的那个失败是无声的:在这个框架之前,两个
共用短名的包会产出一个页面,而且不报任何错。

## 插件

按配置加载,按固定顺序调用 —— 见[插件](plugins.md)。有两点值得在这里重申:

- 每个钩子都是隔离的。它抛异常,内核警告、丢弃这次产出,继续。
- `enrich_remote` 跑在分面、区块、行**之前**,所以从网络解析到数据的插件仍然能
  改变一个包的分类。

## 增长、历史与贡献者

`data/git_history.py` 回放 `pkgs/` 的提交日志:

```
git log --name-status --format="C\t%H\t%aI\t%an\t%ae\t%s"
```

按顺序应用新增、删除和重命名,得到每次提交之后仍然存活的描述符路径集合,以及该
集合的每日快照。由此得到:增长曲线、历史线,以及 —— 因为快照是路径集合而不是
计数 —— 事后才能算出的、按分面拆分的增长曲线。

**回放会自我校验。** 末尾那个路径集合必须等于磁盘上真实存在的 `.lua` 文件。对不
上,就说明曲线在某处说了假话,构建会讲出来:工作树干净时(或加了 `--strict`)是
错误,工作树脏时是警告 —— 未提交的本地改动完全可以解释这种不一致。

### 谁是同一个人

`data/identities.py` 用并查集按登录名、邮箱、姓名合并 git 作者,在有 token 时叠加
GitHub commits API 的 作者→登录名 映射,过滤机器人,并应用
`.xpkgindex/identities.json` 处理自动化解决不了的情况。一个 `Person` 会保留它合并
过的每一个名字,这正是「谁添加了这个包」能匹配上一个用三种写法署过名的人的原因。

## 网络,以及没有网络时

`data/github.py` 是一个小缓存,背后是一份提交进仓库的 JSON
(`.xpkgindex/cache/github.json`)。它只存**投影过的字段** —— 站点会渲染的那几个
值 —— 而不是原始 API 响应。

- `--offline` 完全不碰网络,原样使用缓存。
- `--refresh` 忽略新鲜度全部重抓。显式执行,并提交结果。
- 其他情况下,过期的条目才会刷新。

每次抓取失败都返回 `None` 而不是抛异常。被限流或断网的构建会产出一个完整、只是
少了些点缀的站点 —— 对一个每次合并都要在 CI 里构建的站点来说,这是正确的取舍。

插件在 `enrich_remote` 里拿到的是同一个缓存。缓存事实,不要缓存结论:缓存下来的
「这是个模块化包」把今天的规则冻结进了上个月的数据,而缓存下来的模块名允许规则
改变、并在离线状态下重算。

## 文档

`guides.py` 渲染仓库里已有的 markdown —— 配置指向的是已经存在的文件,所以站点不会
和文档走散。允许原始 HTML(这些文档也是写来在 GitHub 上读的,那里 `<details>` 很
常见);信任级别与仓库自己的 `.lua` 描述符和插件相同,而这两者构建本来就在执行。

## 渲染

`render.py` 为每种配置的语言产出一份完整的静态站点 —— 默认语言在根,其余在
`/<tag>/` 下。URL 是目录形态(`/packages/<slug>/`),因为那是服务端路由可以原样
接管的形状。

有两样东西是生成的而不是静态的:`theme.css`,来自配置里的令牌;以及附加在 CSS 和
JS URL 上的内容哈希。这个哈希不是过早优化 —— 开发期间,一份过期的缓存样式表两次
让一个正常工作的功能看起来像坏了。

`serialize.py` 是数据与渲染之间的边界:站点知道的一切都经由它进入 `index.json`,
所以 JSON 不会悄悄落后于页面。
