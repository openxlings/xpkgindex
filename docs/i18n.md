# Internationalisation

**English** | [简体中文](zh/i18n.md)

The framework translates its own chrome. It never translates anything an index
writes — it only renders what you wrote, in the locale the reader is looking
at.

```jsonc
"languages": ["en", "zh", "zh-Hant"]
```

The first locale is the default and lives at the site root; the others are
generated as complete static sites under `/<tag>/`. A translated page is real
HTML at a real URL, so it is indexable and shareable rather than a client-side
re-render.

Built-in chrome catalogs: `en`, `zh` (简体中文), `zh-Hant` (繁體中文). Common
tags are normalised — `zh-CN`, `zh-Hans`, `zh-SG` → `zh`; `zh-TW`, `zh-HK`,
`zh-MO` → `zh-Hant`.

## Your own text

Any string the index supplies — in `.xpkgindex.json` or from a plugin — may be
a per-locale map instead of a plain string:

```jsonc
"site": {
  "title": { "en": "mcpp Package Index", "zh": "mcpp 包索引", "zh-Hant": "mcpp 套件索引" },
  "description": { "en": "Modular C++23 packages", "zh": "模块化 C++23 包" }
},
"install": { "primary": { "label": { "en": "Install mcpp", "zh": "安装 mcpp" } } },
"docs": { "cta": { "title": { "en": "Quick start", "zh": "快速开始" } } }
```

A plain string means "the same in every language", so nothing has to change
for a single-language index.

Resolution falls back through the exact tag (`zh-Hant`), its primary subtag
(`zh`), the site's default locale, and finally any value present. A
half-translated config still renders something everywhere rather than a blank.

### From a plugin

The same maps work for facet labels, facet values, block titles, badges, row
leads and notes:

```python
def _t(en, zh, hant):
    return {"en": en, "zh": zh, "zh-Hant": hant}

Facet(key="surface", label=_t("how you use it", "怎么用", "怎麼用"))
Block(kind="kv", title=_t("Build", "构建", "建置"), data={"items": items})
```

**Leave identifiers alone.** `import`, `#include`, `modules`, `targets`,
`programs`, `aliases` are either what a reader types or what the manifest calls
the field. Someone comparing a package page against a `.lua` descriptor needs
to see the same word in both.

### `index.json`

Per-locale maps are flattened to the site's default language there. `index.json`
is one document at one URL and schema 1 promises strings; a consumer that
suddenly received `{"en": …, "zh": …}` where it expected a label would break.
Translations live in the rendered pages.

## Documents

A doc entry declares its translations, and the body follows the header's
language switcher:

```jsonc
{ "slug": "quick-start", "title": { "en": "Quick start", "zh": "快速开始" },
  "path": "docs/quick-start.md",
  "translations": { "zh": "docs/zh/quick-start.md" } }
```

A locale with no translation shows the closest one it has — a Traditional
Chinese page falls back to the Simplified document rather than to English, and
an index that ships only English docs shows English docs everywhere. That is
honest about what the maintainers actually wrote.

Two rules decide what the page and the navigation are called:

- The **page heading** is the document's own `# H1`, removed from the body so
  it is never printed twice.
- The **navigation label** is the configured `title` when it names this locale
  explicitly — that is the short name written for the nav, and it is the only
  thing that can be right when the document itself is not translated.
  Otherwise the H1.

### The hand-written language line

Docs written to read on GitHub often start with one:

```markdown
# Quick start

**English** | [简体中文](zh/quick-start.md)
```

On the site that is a second, worse switcher pointing at raw `.md` files, so it
is removed from the rendered page. The test is exact rather than a guess at
what a language line looks like: a leading paragraph whose links *all* point at
another declared translation of this same document. An ordinary link to another
doc is content and survives.

## What the visitor gets

On first visit, the language is chosen from `navigator.languages` against the
`hreflang` alternates in the page head, and the query string is preserved
across the redirect. Once a visitor picks a language from the switcher, that
choice is stored and the automatic redirect stops overriding it.

The same applies to the theme: the OS preference is followed until the visitor
uses the toggle.

## Adding a UI language

The chrome catalogs live in `xpkgindex/i18n.py`: add a dict of the same keys,
register it in `CATALOG` and `LANGUAGE_NAMES`, add any tag aliases, and it
becomes available to every index. Missing keys fall back to English rather than
rendering blank.
